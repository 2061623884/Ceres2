## Finding

P2 — A late order-state response can overwrite a newer order view. T05 explicitly requires “同订单/异单、关闭重开和前后导航”; story 13 preserves sequential simulated order progression. In `frontend/src/SimulatedOrders.tsx::SimulatedOrdersScreen.advance`, the awaited A response unconditionally calls setSelected(current); its failure unconditionally clears selection and sets a global error. The Back button remains enabled during advancement, and the user can then open B. If A settles afterward, success replaces B with A, while failure closes B. Subsequent “联系墨墨” therefore follows the wrong displayed order after a successful stale response. `open` similarly has no request-generation fence against out-of-order detail responses.

Fence detail/advance completion by the current navigation generation and selected order; an A result may update A's list record without taking over B's detail. Scope busy/error cleanup to the same operation and invalidate on Back/unmount. Add delayed success and failure regressions across A→Back→B. This is still present at the fixed product pin; an in-progress test is not a fix. No evidence here of a backend cross-order write or owner bypass.
