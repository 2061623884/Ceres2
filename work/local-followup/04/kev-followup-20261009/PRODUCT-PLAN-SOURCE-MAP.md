## Current request-to-plan path

1. Pi tool contracts live in `runtime/pi/src/worker.ts`: `search_products` accepts `query` and/or `category_id`; `compare_products` also accepts brand, packaging, and pack-count mode. `propose_purchase` requires a product ref and positive package count; `product_details` is read-only. Shopping tools are available after the `guide_request` classification permits shopping (`prompt-modules.ts`). The real Pi SDK runs with `thinkingLevel: 'off'` in this worker.
2. Python receives each tool call in `PiProductRuntime._tool`. For `search_products`, it invokes the injected `ComparisonService.search(..., scope_to_page=False)` callback, maps returned rows to run-local refs, and sends those rows back to Pi. `compare_products` uses the page-scoped callback and publishes candidate refs. `product_details` reloads the current product/Offer. `propose_purchase` resolves a current or displayed ref and stores the corresponding SKU and quantity; it does not write the cart.
3. `ComparisonService.search` merges current task conditions over same-named tool arguments, applies the current category/page scope, and calls `CatalogService.search_products`. It then applies product, Offer, activity, dietary/safety, brand, packaging, pack-count, and exclusion filters. `ProductQuestionService.explore` follows a similar retrieval-and-filter path for explicit constrained exploration and creates a durable question from the resulting supply.
4. `CatalogService.search_products(q=...)` builds the approved SKU allowlist (and category restriction), asks `KnowledgeService.search` for all eligible IDs, validates the retrieval manifest, then re-reads canonical product and current store Offer rows. Each returned hit carries retrieval ranks/scores, RRF score, corpus revision, and index revision. Without `q`, it returns approved catalog rows in SKU order. Price/stock are read from Offer, never from the retrieval document.
5. `app/knowledge/hybrid.py` tokenizes Chinese into character unigrams/bigrams and lowercased ASCII tokens; it combines sparse BM25 and dense BGE ranks with RRF (`k=60`). It returns candidates and relevance-qualified hits, using the calibrated floor or a literal source match. Relevance filtering is not eligibility: business constraints run downstream.
6. `PiProductRuntime._answer_value` validates final refs against this run's refs and produces selected product evidence. A purchase proposal is converted in `PiProductTurnService` into `PurchaseService.prepare`, `prepare_selected`, or `prepare_dish`; a displayed comparison ref is re-resolved and checked against the proposal SKU first. `PurchaseService.facts` checks canonical SKU, current Offer, sellability/quantity, activity and product constraints, delivery, and budget. Plan preparation stores the validated plan and renders it; confirmation is a separate operation. `confirm` rechecks versions, displayed plan, current Offer and selected quantities before the atomic cart/ledger/receipt write. A plan, selection, accepted quote, or retrieval result alone is not confirmation.
7. Clarification is a distinct observable outcome. Pi can return a bounded waiting slot (`target`, `packaging`, `brand`, or `budget`); turn publication stores `pending_clarifications`. The public product question flow can also persist category/product options, then validate answers against the active question and fresh supply. Neither waiting path creates a plan or cart write unless a later explicit user action does so.

## Existing public HTTP evidence

- `backend/tests/test_runtime_pi_product_query.py` uses the real Pi SDK/stdio and Guide SSE with a deterministic controlled model and an isolated one-SKU database. It covers search→details→grounded reply, category search, a forced packaging clarification, the five-tool-round/15-second limits, untrusted refs, empty-selection semantics, owner/session replay, stop, and provider errors. `backend/tests/conftest.py::controlled_product_source` supplies synthetic literal product recall and explicitly says it does not test BGE quality or a real built index.
- `backend/tests/test_purchase_public.py`, `test_purchase_confirmations.py`, and `test_purchase_safety.py` cover a public Pi proposal→persisted plan with an empty cart, explicit confirmation, replay/idempotency, stale or changed Offer/conditions, and cart write safety.
- `backend/tests/test_guide_clarification_context.py` covers durable clarification, an elliptical answer resolving the saved question, task changes, and unrelated/progress turns. `test_next_guide_gate_public.py` covers the public role-entry decision boundary.
- These tests are strong boundary/transaction evidence, but their controlled model and product recall do not establish primary-Pi behavior on the public 40 cases or real hybrid-index candidate quality. They also do not establish Kev's routing/policy-classification behavior. Source-level RRF configuration is not runtime retrieval evidence.

## What a public failed-run trace can show today

The Guide receipt has `runtime_events`, `runtime_summary`, and final `product_evidence`; session state exposes the plan, comparison cards, active question, and current conditions. Retrieval events currently retain namespace, retrieval ID, outcome, duration, and source/index revisions, but not the query or hit IDs. SDK events retain lifecycle/tool name and tool-call ID, not tool arguments/results. `product_evidence` contains products selected in a completed result; the current baseline runner's capture-v2 projection omits that field, while a purchase proposal's public after-state plan carries its SKU/quantity. Captured public messages show what the user saw, not hidden tool payloads. These limitations are source observations; they do not establish which observation mechanism the later evaluation needs.

After a labeled public failure identifies a concrete diagnosis gap, first inspect the existing public receipt and evaluation export. If those do not expose the needed evidence, an eval-owned, temporary, PUBLIC-only tool-boundary observer could be considered to correlate the actual query/constraints, Catalog-returned SKU IDs and retrieval metadata, post-filter SKU IDs, and final Pi-selected refs/SKUs for that execution. Whether such an observer is necessary, and where it belongs, remains unresolved until an actual labeled failure is examined. This does not presume a production trace, schema, configuration, or runner-field change. Avoid full prompts, provider output, and database rows; current Offer facts remain available through public state/catalog projections.

## Open questions, not conclusions

- Source code shows current task conditions override same-named primary-Pi search arguments in `ComparisonService`; this may preserve explicit task constraints, but whether it causes any public case failure is unproven until compared with the user-confirmed 02 labels and available public evidence.
- A specific SKU may be absent because it did not pass retrieval relevance, because downstream constraints excluded it, or because Pi did not select a returned ref. Existing capture-v2 alone cannot reliably distinguish these cases.
- Whether primary Pi/DeepSeek chooses the right query/tool, selects the correct returned candidate, asks when needed, or completes both halves of a mixed request is unproven by controlled-model tests and source inspection. Kev's route/policy judgments are a separate unproven dimension. Do not tune prompts, worker behavior, thresholds, or Offer facts until a labeled public failed run identifies the failing layer.
