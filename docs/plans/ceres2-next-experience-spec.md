## Problem Statement｜用户问题

用户希望在同一个可信购物体验中，从“来点零食／喝的”这样的模糊需求出发，看到真实可选的类别和商品，保持预算与饮食条件，选择后完成明确确认；也能随时问政策、处理订单，再由自己选择回到选购。当前 Ceres2 已有购物、记忆、模拟结算和售后权威服务，但页面选项身份、供给差异、角色导航和表达时序尚未构成经过验证的完整体验。旧系统已有视觉和业务设计，不能靠复制旧运行库或引用旧测试通过来证明新系统完成。

“看到按钮”“模型说成功”“接口局部通过”分别不等于可追溯选择、业务已完成、真实页面已验收。新体验必须减少重复提问和等待，仍保留事实、身份、版本、确认与幂等边界。

## Solution｜解决方案

以 Ceres2 实际 Pi 售前、LangGraph 售后和 Python 权威业务服务为基础，采用已确认的最新 Ceres 页面设计，贯通以下用户旅程：

1. 零食／饮品的真实供给驱动探索、分类、筛选、选品、清单及明确加购确认。
2. 两角色共享一般政策问答；一次 Kev 决定所有新文字的职责归属，并为可可职责内请求给出有界能力标签；Mercury 保留自身售后处理，用户选择后才跨角色跳转。
3. 结构化按钮直达确定性服务；真实结果先显示，再流式补简短自然介绍。表达失败不改变业务结果。
4. 已有首页“减脂活动”卡进入限定主题成品集合，沿用选品与确认。
5. 购买、独立模拟结算、售后申请与返回选购，复用现有事务与人工保护。
6. 按需组织 Prompt，先验证语义等价，再受控优化自然表达和调用成本；同一候选完成公开 API／SSE、真实模型、真实页面及本人验收。

V3／后续体验材料中的业务要求默认继承，本轮明确覆盖以最新决定为准。配送新能力和模型选型不属于本阶段。

## User Stories｜用户故事

### 真实供给与选购

1. 作为购物用户，我希望说“来点零食”后只看到当前供给支持的有意义类型，以便选择真正买得到的方向。
2. 作为购物用户，我希望说“想喝点东西”时能看到实际存在的饮品类型，以便不用凭空猜商品名称。
3. 作为已有具体需求的用户，我希望说清类型或商品后直接看到商品，以便不重复回答分类问题。
4. 作为购物用户，我希望仅在跨类型区别仍待选择时被问分类，以便候选数量多不会变成强制问卷。
5. 作为比较商品的用户，我希望同类商品按真实口味、品牌、规格展示区别，以便根据事实挑选。
6. 作为预算有限的用户，我希望类别和筛选变化继续保留预算、数量和有效条件，以便不反复纠正。
7. 作为有饮食限制的用户，我希望硬约束不被静默放宽，以便避免收到不适合的推荐。
8. 作为购物用户，我希望一次只回答一个当前必要问题，以便保持对话简洁。
9. 作为购物用户，我希望信息足够时直接推进，以便不必把每个字段逐项填写。
10. 作为购物用户，我希望能点气泡也能用文字回答，以便按照习惯表达。
11. 作为购物用户，我希望点击相同文案的选项仍能绑定正确问题，以便不会选错对象。
12. 作为购物用户，我希望已回答的气泡留在历史、标记所选并禁用，以便看懂过程且不重复执行。
13. 作为购物用户，我希望临时查购物车后仍能回答原问题，以便插话不会丢失进度。
14. 作为购物用户，我希望取消、换目标或改变候选条件后旧气泡失效，以便旧选择不会污染新任务。
15. 作为购物用户，我希望刷新和断流恢复后看到权威的当前问题与结果，以便不靠模型猜测进度。
16. 作为购物用户，我希望库存或报价变化时得到明确更新，以便旧卡片不会执行过期交易。
17. 作为购物用户，我希望没有匹配时保留原条件并解释原因，以便由我决定是否改变可调整条件。
18. 作为购物用户，我希望未知营养、规格或政策事实保持未知，以便不被编造信息误导。
19. 作为购物用户，我希望商品展示区分商品身份、可售 Offer、销售包装和包装价格，以便理解买到什么和实际花费。
20. 作为购物用户，我希望选类别或选商品不会自动加购，以便保留最终决定权。
21. 作为购物用户，我希望清单仍支持多选和明确确认，以便一次购买多个需要的商品。
22. 作为购物用户，我希望重复点击确认只产生一次业务效果，以便不会多买。
23. 作为购物用户，我希望计划修改后重新确认准确的当前清单，以便旧同意不会授权新商品或新价格。
24. 作为做饭的用户，我希望单菜、人数、多菜合并和包装换算继续可用，以便新体验不破坏已有能力。
25. 作为遇到缺货的用户，我希望继续选择替代或部分采购，并单独确认加购，以便保持真实供给和授权边界。
26. 作为复购用户，我希望历史采购按当前供给和条件重建、标明差异，以便不把历史价格或同意当成现在有效。

### 角色、政策和恢复

27. 作为任一角色页面的用户，我希望没有选择订单也能问一般售后政策，以便先了解条件。
28. 作为政策咨询用户，我希望回答带适用条件和来源，以便区分一般规则与自己的订单资格。
29. 作为购物用户，我希望每条新自由文字只经历一次 Kev 判断，以便不重复路由和增加无用等待。
30. 作为购物用户，我希望四类能力标签仅帮助可可选取上下文，以便复杂多目标文字仍由可可主模型理解，售后继续按其自身职责处理。
31. 作为闲聊用户，我希望普通闲聊不会创建采购任务，以便没有无意的业务副作用。
32. 作为跨职责提问的用户，我希望自己选择后才跳到目标角色页面，以便角色不会擅自改变。
33. 作为缺少信息的用户，我希望留在当前角色澄清，以便缺字段不会被误判为需要转接。
34. 作为遇到服务故障的用户，我希望看到真实故障和可用手动入口，以便失败不会被伪装为分类成功。
35. 作为拒绝切换的用户，我希望本次 opening 不反复收到自动提示，以便选择得到尊重。
36. 作为刷新页面的用户，我希望已显示的自动提示额度仍被记住，以便刷新不会重复打扰。
37. 作为关闭后重新打开聊天的用户，我希望新 opening 恢复一次自动提示机会，以便新的使用周期正常工作。
38. 作为手动切换的用户，我希望只续接仍有效的意图，以便过期请求不会突然执行。
39. 作为明确要求返回购物的用户，我希望直接执行这个导航意图，以便不再次确认同一跳转。
40. 作为接受转接的用户，我希望目标角色接住原始请求并重新查询事实，以便不用重复描述也不依赖过期摘要。
41. 作为用户，我希望新页面仍保留比较、清单、订单、售后、人工、停止与恢复入口，以便视觉更新不会丢失功能。

### 结果表达和主题成品

42. 作为点击分类／筛选的用户，我希望真实商品卡先显示，以便不必等待介绍才能选购。
43. 作为购物用户，我希望卡片后流式出现简短自然介绍，以便交流有活人感且基于真实结果。
44. 作为用户，我希望介绍失败时结果保留、加载结束，以便已经完成的动作不被隐藏、回滚或重做。
45. 作为用户，我希望自然介绍不会重筛选、重加购或改写回执状态，以便表达和业务事实保持一致。
46. 作为用户，我希望两角色简洁地先说结果再说必要下一步，以便快速理解当前状态。
47. 作为用户，我希望按需加载上下文后仍保留来源、条件和复杂需求，以便速度优化不牺牲正确性。
48. 作为首页用户，我希望点击已有“减脂活动”卡进入相关成品集合，以便快捷挑选主题商品。
49. 作为主题购物用户，我希望沙拉、拼盘和饮品按成品出售，以便不会被自动拆成食材采购。
50. 作为主题购物用户，我希望主题内仍遵守预算、库存和确认规则，以便活动入口不是交易特权。
51. 作为主题购物用户，我希望主题外的新需求能明确退出或更新当前目标，以便不会暗中混入不相关商品。
52. 作为主题购物用户，我希望活动日期、折扣或健康宣称都有事实依据，以便名称不会被当成减脂效果证明。

### 售后、记忆与验收

53. 作为购买用户，我希望确认加购后仍单独进行模拟结算，以便清楚区分购物车和订单。
54. 作为新订单用户，我希望售后角色能查询这笔订单，以便不出现另一套演示订单。
55. 作为售后用户，我希望先看到具体资格和申请提案，再明确确认提交，以便切角色或选订单不被当成申请授权。
56. 作为售后用户，我希望提交成功明确表述为申请已提交，以便不会误以为退款已到账或退货已完成。
57. 作为售后用户，我希望重复提交或断流重试返回原回执，以便申请不会被重复执行。
58. 作为售后失败的用户，我希望失败被保留并暂停该步骤，仍可选择去购物，以便不会用购物结果掩盖售后失败。
59. 作为完成售后的用户，我希望选择回购物后能寻找替代商品，以便已完成的申请不被重放。
60. 作为人工接手中的用户，我希望 Agent 尊重人工负责期间的写保护，以便同一事项不会并发处理。
61. 作为使用记忆的用户，我希望显式保存、更正和删除继续有效，以便后台提取不会覆盖我的新决定。
62. 作为复购用户，我希望记忆只帮助偏好理解，以便它不会代替库存、价格、订单或当前授权。
63. 作为用户，我希望重启恢复和自动记忆／Dream 的实际行为有独立验证，以便“已有代码”不会被当成已验收。
64. 作为验收用户，我希望看到同一候选的真实页面、模型和逐轮业务证据，以便判断完整体验而非混合历史成绩。

## Implementation Decisions｜实施决定

### 1. 单一权威与适配方式

保留 Python 确定性业务权威、实际 Pi 售前和实际 LangGraph 售后。前端只展示和传递受验证引用；模型／checkpoint／聊天记录不成为购物车、订单、申请或授权的第二权威。复用 Catalog、Comparison、Purchase、Supply、History、Memory、Checkout、售后及人工服务。迁移单位是业务行为、最小静态数据与 UI 适配，不是旧 loop、旧运行库或旧数据库。

同一用户身份、展示版本、供给重新校验、写入与回执原子性、幂等、人工责任代际继续适用。选类、选品、切角色、选订单均不构成加购／结算／售后提交授权。模拟业务没有真实支付或履约。

### 2. 最小问题／动作合同

优先复用 session、business task、turn/run、版本、displayed refs、pending clarification、事件与回执。仅在现有记录不能唯一表达当前问题／选项或恢复时，补最小合同；不新增通用状态层、万能 pending store 或 workflow 引擎。

问题和选项需有稳定身份及原始展示关联，绑定当前用户、任务与适用版本。标签只是展示；不同问题的相同标签不能合并为一个动作。服务校验当前问题、选项成员资格、事实新鲜度与操作类别。选择与后果确认分开。已回答问题留历史、标所选且不能重复改变状态。旁支只读查询不无故失效；取消、新目标或影响候选条件的变化使其更新／失效。发出问题即结束本 run，后续回答是新 turn，不挂 worker 等人。

纯结构化有效动作零 Kev，直接进入确定性服务；自由文字（包括“第二个”或夹带新的限制）作为新文字处理，不丢条件，不从含糊文字升级交易授权。无效／过期动作受控拒绝或重取当前展示，不将旧标签交给模型猜测执行。

### 3. 供给设计与最小可复现数据

区分商品 SKU 身份与当前店铺可售 Offer。商品类型、品牌、口味、规格、包装单位、每销售包装价格、库存状态和属性证据须来自当前权威数据；未知即未知。饮食／过敏约束不得以模型推测补齐。分类选项来自已经满足当前有效约束的真实供给，有意义的跨类型区别才触发提问。同类数量多不触发分类。

以以下用例族决定最小数据，数量由覆盖必要差异决定，不设虚构完整商品表：

| 用例族 | 必需供给结构（是设计要求，不是现存商品断言） | 可观察行为 |
|---|---|---|
| SN-正常 | 至少两个有业务差异的零食类型，各有可售代表项 | 泛需求选类，具体类型直接商品，确认前无购物车写入 |
| SN-缺信息 | 已有候选但数量／必要包装等尚不能确定 | 只问当前必要信息，文字足够后推进 |
| DR-跨类 | 实际可售且满足约束的不同饮品类型 | 简短概览与真实类型选项 |
| DR-同类 | 同类中存在可验证品牌／口味／规格差异 | 直接商品，属性筛选不造新分类 |
| SUP-不足 | 可售、缺货／库存不足、未知属性、无匹配可切换的固定状态 | 保留条件；明确无结果；可调整条件由用户选 |
| PKG-报价 | 同一商品不同可售包装或份量边界，已知包装价格 | 包装量／数量／总价与实际 Offer 一致 |
| TOP-成品 | 已有活动范围内真实成品沙拉／拼盘／饮品（按当前可得供给选择） | 限定候选，不拆成食材，不造活动机制 |
| ORD-售后 | 由独立模拟结算生成、资格内／外与人工负责场景 | 当前订单查询、提案、确认、重复回执、写保护 |
| MEM-复购 | 受控历史采购与显式／自动记忆版本 | 当前供给差异、纠正删除与后台竞态可重现 |

实施时先盘点已有静态数据，仅补缺失差异；每个 fixture 记录来源、适用场景、版本和唯一维护人。可重复导入且不污染真实／旧业务状态；不导入旧 session、cart、order、checkpoint、凭据或私有 holdout。正常、缺必要信息、多候选、缺货／无匹配必须逐项映射，不能靠增加商品数冒充模型改善。

### 4. 一次 Kev 与用户控制的角色导航

所有新自由文字 turn 各一次 Kev 判断职责归属；同次联合判断中的探索／采购修改／事实问答／闲聊四类有界能力标签仅服务于可可职责内请求，不强制套用于 Mercury。Mercury 保留 LangGraph、政策及售后能力边界，不新建四类售后能力枚举，也不为此再调一次 Kev。可可标签仅用于选择相关 Prompt、工具和上下文；不排工具顺序、不抽业务参数、不判断参数完整性、不授予权限。复杂多目标仍由当前角色主模型统筹；标签不能裁掉用户需求。同请求重传、工具结果、恢复和接受转接不重复路由。

职责不匹配才提示用户选择页面跳转；信息不足和服务失败留当前角色澄清／恢复。一般政策在两角色都可答，不因未选订单强迫切换。自动切换提示每 opening 最多一次，在显示确认后消耗；拒绝与角色切换不重置，刷新保留，显式关闭重开才重置。明确返回请求不重复征求同一导航同意。手动入口只续接有效待处理意图，Kev 失败可见且不伪装成成功判断。

交接主要带触发跳转的原始请求，只有定位所需时附商品／订单标识；目的角色重查事实。完整历史、复杂摘要、条件／结果包不是强制合同。不暗中调用另一角色完成业务，不做多 Agent 对话。

### 5. 最新页面与已有保护并存

复用已确认 Ceres 的统一聊天浮层、角色胶囊、页面跳转与视觉方向，适配 Ceres2 当前严格输入、版本锚点、展示引用及持久 SSE。不能直接用旧 App 请求体覆盖新接口。通用候选组件保留未知属性、多种包装和现有预算／排除条件；不退回可乐专用 UI。购物清单、供给替代、报价、历史、订单、售后提案、人工、停止与恢复入口保留。实际按钮可键盘操作，忙碌／错误／失效状态可见。

### 6. 双角色一般政策及售后闭环

一般政策无需订单，回答包含来源与适用条件，不推断具体订单资格。具体资格、提案和申请从现有订单权威查询；整单退款／整行退货规则不在本轮改变。购买→独立模拟结算→售后提案→确认申请→用户选择回购物形成一条旅程。申请提交不等于到账；失败保留且暂停，完成步骤不重放；目的角色按必要标识重查。人工负责期间沿用责任保护，不引入实时客服或第二售后数据库。

### 7. Prompt 先等价，再优化

先冻结业务已可用基线，将公共表达、角色职责、可可四类能力、Mercury 自身政策／售后能力及当前事实按需要组织，验证语义保持；再优化自然中文、冗余上下文、调用和 token 成本。优化不得省略事实来源、有效约束、失败状态或确认边界。两角色共用模块唯一维护，修改与测量基线配对，避免并行改写使对照失效。未知 token 不写零，不预设节省比例或新的成功 SLA。

### 8. 结果先行与自然表达隔离

R10／R11 已确认：分类／筛选后需要主模型简短自然介绍；真实卡片／业务回执先显示，再流式补介绍。结果来自确定性服务，表达模型只能解释这份真实结果，不重新理解、筛选或执行。表达失败、超时或中断保留业务结果并结束加载；不回滚、不重提已完成动作。已有受校验最终文本切块不等同于原始 token 实时流；新实现必须证明卡片先可用，且至少在介绍生成完成前，已产生并通过必要事实约束的内容开始到达客户端；不得仅在完整生成后切块冒充流式生成。记录生成开始、首个介绍片段、生成结束及客户端到达时间，保留必要事实缓冲，不为追求原始流输出不实内容。SSE 重连以既有事件／回执恢复，不能触发新业务效果。

### 9. 首页活动

只接现有“减脂活动”卡与限定成品选购链路；GREENRESET／FreshBreak 仅供灵感，不授权新平台、日程或叶子奖励。真实成品不自动拆食材。主题外新意图按现有目标变更语义更新／退出并使旧问题正确失效。日期、折扣、功效均需事实来源；活动名称不证明减脂效果。

### 10. 迁移纪律与责任

旧源业务默认继承，当前明确覆盖优先。每个纵向切片包含需要的数据／schema、业务 API、UI、测试和证据，不设只铺基础设施的绿地票。共享页面外壳、选项合同／schema、商业事务、单次 Kev、Prompt 与数据清单各有唯一合入负责人；独立工作可并行，共享改动排期不伪造成业务依赖。正式实施前重核源 SHA、相关规范与工作树状态，不覆盖旧 dirty checkout。具体文件布局和字段名由实现接缝决定，本节不以易过时路径冻结架构。

## Testing Decisions｜测试决定

### 主接缝与好测试

已批准方案使用最高可行公开接缝：现有公开聊天／业务 API 的多轮旅程和 SSE，加真实页面点击；通过正常查询接口检查购物车、订单、申请和当前问题。已有 Ceres2 HTTP／SSE、确定性服务事务、版本确认、恢复及受控模型测试为先例。只对必要边界补低层测试，不另建测试专用产品 API 或评测平台。

断言用户可观察结果、结构化选项身份、保留条件、已展示对象与实际业务状态，而非内部节点名称、函数调用数量或固定文案。唯一必要调用观测是已承诺的新文字一次 Kev、有效结构化动作零 Kev及真实表达调用，作为边界／成本证据，不规定无关内部实现。自然表达人工审阅简短、可读、事实准确和下一步清晰，不以逐字匹配衡量。

### 必须覆盖的行为矩阵

- 零食、饮品跨类、同类属性、具体需求直达、文字与按钮混用、清单多选、预算／数量／安全条件保留；信息足够不再问。
- 同名选项、已回答历史、旧问题、旁支购物车查询、取消、新目标、条件改变、报价／库存改变、重复点击、并发文字／点击、跨用户／跨任务引用。
- 刷新、SSE 重连、停止、显式关闭重开和服务重启分别验证，不以一个“恢复通过”概括全部。
- 新文字职责路由、重放免再路由、可可四能力与 Mercury 自身职责不混同、复杂多目标、无订单政策双角色等价、接受／拒绝／明确返回、opening 提示 ACK 与额度、Kev 故障、手动有效／过期续接。
- 单多菜／人数／包装／比较／替代／部分采购／历史复购；改清单旧确认失效、重复确认和结算原子回执。
- 卡片／回执先于介绍可用，介绍基于同一结果流式追加；表达失败保留结果且无重筛选／重写入／长挂加载。
- 活动入口、限定成品、真实包装与报价、无匹配和主题退出，功效／日期／折扣不编造。
- 新购订单售后资格、提案／确认、申请不等于到账、失败后购物、成功后不重放、人工责任保护。
- 显式记忆 CRUD、角色边界、自动提取与显式更正／删除竞态、重启、Dream 阈值／冷却及真实生命周期；记忆不代替商业事实。

### 分层证据与门槛

每票在依赖放行前完成其必要技术行为及证据，不能把第一次真实 UI 点击、身份合同、确认保护等全部推迟到最终票。受控测试、真实 Kev／主模型、真实页面、自然语言审阅和本人验收分开记录；缺条件明确阻塞／未验证，不能用跳过当通过。测试、lint、typecheck、build 和安装验证由专职 Tester 执行；Standards／Spec 两轴独立只读审查。当前仅编写计划，没有执行这些活动。

零严重越权、错单、擅自切换、重放完成步骤或编造商品／政策事实是硬门槛。技术证据满足可放行依赖，不要求用户先完成逐票体验验收；技术交付记待验收，只有满足约定并完成人体验收才记已验收。

### 基线、性能与独立评估

冻结源码（含未提交源码清单／哈希）、数据／供给、实际模型配置、实际 Prompt、用例与运行环境。继承能力对照冻结 V3；路由／Prompt 改善对照独立 business-ready 基线，固定数据避免把供给扩张算作模型增益。保留逐轮原始输出、状态、决策、来源、错误、耗时、真实调用和 token；失败也保留。

开发、回归和 holdout 按场景隔离，同义改写归同组。实现者不读私有 holdout；冻结候选后独立执行，修复后原集只能算回归，不能重称新独立评估。最终所有旅程在同一源码／数据／Prompt／模型候选复核，不拼接旧成绩。记录样本量、冷启动等条件，不夸大统计意义。

分别测首次可见状态、首个有用事实内容、结果卡可操作时点、自然介绍首段与完成、完整任务耗时、失败／保护触发、调用与 token。Ceres2 导购 30 秒／5 轮、售后 15 秒为保护上限，不是成功 SLA；历史 V3 Q20 只作为适用版本来源记录，不自动成为本候选硬阈值。本轮不选模型，也不承诺未量测的性能提升。
