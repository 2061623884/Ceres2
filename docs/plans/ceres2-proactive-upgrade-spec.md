# Ceres2：主动导购、受控售后与 V1/V2 业务延续规格

2026-10-05 15:42 UTC：干净重建与持续实施已获授权。16 项目标、批准依赖与测试接缝保持不变；所有新工程技术验收重置，旧通过仅为归档参考。保留现有前端，Python 业务与 Pi/LangGraph runtime 从干净目录选择性实现；不迁入旧运行状态。所有测试命令仅 Tester 执行；不推送。

## Problem Statement

用户需要把自然语言购物目标变成满足人数、预算、排除条件和模拟门店供给的购买方案，并自主决定选什么、何时加购。现有导购固定路由不能充分根据查询结果继续探索；长期对话、比较、显式记忆与历史复购存在连接缺口。前端本地订单不能成为持久订单权威，Mercury 的手写循环、演示用户回退和直接写工具无法保证具体确认、恢复与身份隔离。

Ceres2 必须延续 V1/V2 的完整业务范围，同时实际采用 Pi 和 LangGraph。不能把运行引擎重构变成删减业务，也不能要求先恢复整套采购闭环才让两个新 runtime 可演示。历史验证和当前云端结果必须分开：归档工程定向离线基线为 88 passed、10 failed、5 个收集错误，不是全量结论；原 V2 自动记忆的 18.109 秒失败仍是历史未验收事实。

## Solution

保留普通商品浏览、轻量导购入口和独立墨墨入口。同一匿名用户拥有一个长期可可对话、最多一个活动购买任务；一个购买任务可跨多次有界运行。可可使用真实 Pi SDK，在已明确目标内查找、比较、查缺与提出替代；商品、数量、供给与写入结果由 Python 业务服务决定。关联新目标先建议后选定，选定与确认加购始终分开。

聊天保持可响应，支持条件修改、查看进度和停止当前处理。关页后已开始的运行在原预算内继续，结果持久保存；澄清和授权节点暂停等待。每次运行最多 5 轮工具循环并受 15 秒保护边界约束，任一先到就停止探索；可靠结果可提前完成，未完成不自动无限续跑。

保留四类记忆、聊天显式 CRUD、回复后提取和低频 Dream；复购依据历史方案重新计算、重查供给、重新确认。独立模拟结算生成同用户持久订单。墨墨使用真实 Python LangGraph 管理查询、资格、提案、确认、幂等提交与回执；必要时创建精简异步人工工单。价格、库存、订单、支付和售后始终明确为模拟。

## User Stories

1. 作为用户，我希望继续浏览和搜索商品，再按需打开导购，以便无需先进入全屏聊天。
2. 作为用户，我希望重新打开可可仍能查看同一长期对话，以便继续了解以前的采购安排。
3. 作为用户，我希望一次只有一个活动购买任务，以便当前目标与旧历史不会混淆。
4. 作为用户，我希望明确新采购时结束旧任务并保留历史，以便开始新的安排而不丢失记录。
5. 作为用户，我希望追加或修改仍属于当前任务，含糊时先澄清，以便不被误切任务。
6. 作为用户，我希望任务切换或放弃不自动清购物车，以便已加购商品保持原状。
7. 作为用户，我希望模糊购物目标得到必要追问，以便关键信息充分后能直接推进。
8. 作为用户，我希望可可根据查询结果继续查找和比较，以便不必逐次指挥只读工具。
9. 作为用户，我希望商品、报价、库存和配送均有业务事实依据，以便不会依据模型猜测采购。
10. 作为用户，我希望新菜或关联商品先作为建议，以便由我决定是否加入购买任务。
11. 作为用户，我希望单菜人数变化正确换算食材、整包件数和余量，以便清单符合实际需要。
12. 作为用户，我希望明确追加多菜时兼容食材先合计再取整并保留来源，以便避免多买或漏买。
13. 作为用户，我希望基础调料保持可选择、未选不等于家中已有，以便采购事实准确。
14. 作为用户，我希望同食材规格缺货或不足时看到合法适配，以便在预算和条件内选择。
15. 作为用户，我希望完全缺项时先看供给预览，再选择是否部分采购，以便不把残缺方案当完整菜品采购。
16. 作为用户，我希望品类选购可比较品牌、容量、包装、件数和价格，以便看清真实差异与未知信息。
17. 作为用户，我希望当前预算和排除条件始终有效，以便探索不会静默放宽限制。
18. 作为用户，我希望预算协商展示具体总价且接受报价不等于加购，以便分别控制条件与执行。
19. 作为用户，我希望清单支持改选、数量修订和独立确认，以便在执行前确定准确商品与件数。
20. 作为用户，我希望既可按按钮，也可明确说“就按这个加购”，以便确认唯一有效且已展示的方案。
21. 作为用户，我希望“好的”等含糊回答不会触发加购，以便没有明确对象时先澄清。
22. 作为用户，我希望改商品、数量或预算后旧确认失效，以便不把旧授权用于新方案。
23. 作为用户，我希望重复确认只返回同一回执，以便不重复加入购物车。
24. 作为用户，我希望处理购物时还能问无关事实问题或查看进度，以便聊天保持可响应且不误终止任务。
25. 作为用户，我希望修改条件后及时得到回应，有用查询可继续但旧结果重新校验，以便新条件实际生效。
26. 作为用户，我希望“停止当前处理”只停本次运行，以便保留购买任务与已有方案。
27. 作为用户，我希望明确放弃才结束任务，以便停止处理和放弃采购是不同选择。
28. 作为用户，我希望停止与提交竞争时看到实际发生的结果，以便不会误以为已成功加购被撤销。
29. 作为用户，我希望关闭页面后已开始的处理在原上限内继续，回来可见结果，以便断开页面不丢失进展。
30. 作为用户，我希望达到时间或工具轮次上限后看到可靠结果与未完成部分，以便自己决定是否继续。
31. 作为用户，我希望工具动作只占一行滚动替换的灰字，准备回答时先显示三个点再流式输出，以便过程清楚而不刷屏。
32. 作为用户，我希望回复自然、简短、适度使用 emoji，必要时分多条，以便交流连贯易读。
33. 作为用户，我希望通过聊天保存、查询、更正和删除四类记忆，以便管理可可实际使用的长期背景。
34. 作为用户，我希望当前条件优先于旧偏好、已删除或过期记忆不再使用，以便我的新决定生效。
35. 作为用户，我希望回复后自动提取与 Dream 不阻塞主回复，也不把助手建议变成我的偏好，以便记忆可靠。
36. 作为用户，我希望可可与墨墨只读取各自需要的相关记忆，以便共享身份不意味着所有背景都被开放。
37. 作为用户，我希望相关未完成历史清单最多被适时提醒一次，以便被帮助而不被反复追问或自动恢复旧任务。
38. 作为用户，我希望选定历史方案复购时应用当前人数、预算、排除与供给并重新确认，以便旧价格和授权不会被沿用。
39. 作为用户，我希望模拟结算生成持久订单且只移除本次结算商品，以便刷新、重启和并发加购不会丢失结果。
40. 作为用户，我希望从准确订单按钮进入独立墨墨查询，以便无需模型猜订单编号。
41. 作为用户，我希望订单、物流、资格、政策和进度查询不要求额外确认，以便快速了解事实。
42. 作为用户，我希望退款或退货先展示对象、数量、预计金额及条件，再明确确认，以便了解提交内容。
43. 作为用户，我希望换单、资格变化或旧提案失效时重新确认，以便未经当前授权不提交。
44. 作为用户，我希望提交后掉线或图恢复仍得到同一售后回执，以便不会重复申请或误报失败。
45. 作为用户，我希望信息不足先被追问、不符合资格得到解释，以便知道实际原因而不是被自动转人工。
46. 作为用户，我希望明确要求人工、政策无法确定或服务持续失败时有持久异步工单，以便问题不丢失且可查看进度。
47. 作为用户，我希望人工负责期间 Agent 不独立提交同事项写操作，以便不会出现重复或冲突处理。
48. 作为人工处理者，我希望查看关联订单、问题摘要和必要历史，回复或追问并标记解决／关闭，以便完成最小必要处理。
49. 作为用户，我希望人工也不能绕过资格与确认直接退款，以便同一事项遵守相同业务规则。
50. 作为用户，我希望其他访客不能读取或修改我的对话、记忆、车、订单、工单或回执，以便数据按用户隔离。
51. 作为维护者，我希望两个真实 runtime 先用隔离 fixture 独立演示，以便早验证关键集成而不被完整采购恢复阻塞。
52. 作为维护者，我希望每个业务切片带所需数据、迁移和测试，以便可独立重建、验证和安全回退。
53. 作为维护者，我希望离线、真实模型、真实页面和用户本人验收分别留证，以便不会把 mock 或历史成功冒充当前完成。

## Implementation Decisions

### 1. 模块、进程与权威

- 已确认架构为 Python 业务权威＋Node/TypeScript 实际 Pi SDK 售前＋Python LangGraph 售后；不做全量 TypeScript 重写。Pi 管模型—工具迭代，LangGraph 管售后阶段与恢复，二者都不拥有业务写入授权。
- 复用并按需调整身份/对话、目录/Offer/配送、检索、需求/包装、方案修订/刷新、确认/购物车、订单、资格/申请、记忆、操作回执等领域服务。保留能力与契约，不要求逐行保留旧实现；不把旧完整路由包装成一个工具冒充 Pi。
- 规格提出的最小部署接缝为单机 Python 外部 API 主机托管 Node 子进程，使用受控 stdio JSONL，不新增匿名内部 HTTP。协议包含启动、只读工具请求/结果、事件、提案结果、取消、错误；每帧关联 opaque run handle、调用 ID 和序号。首切片一运行一 worker、工具批次显式串行，启动开销须实测；不预建进程池。实现确需改变此接缝时记录证据，不改变已批准产品行为。
- Python 私有运行登记保存可信 owner、task、原始 revision anchor、预算与停止状态；模型参数不得包含可自选的 owner、授权或事务字段。worker 只获得所需模型配置和领域工具，不获得业务数据库访问或通用 shell/file 工具。stdio 与白名单不等于 OS 沙箱。
- 单一业务事实与事务权威沿 ADR 0001 保留。拟将购物车、模拟订单、售后申请与业务回执纳入同一 Python 业务存储事务；Mercury checkpoint 可独立存储，仅保存流程引用。此为落实已确认架构与事务测试边界的最小工程设计，不以旧 ADR 的历史存储建议冒充单独的产品决定；普通适配细节按证据落实，无需逐项再问用户。禁止以两个独立普通 commit 的运行时双写解决订单同步。

### 2. 长期对话、运行与新消息

- 可信匿名 cookie/bootstrap 决定 owner；body、模型、订单按钮和 checkpoint 不得选择 owner。每 owner 唯一长期可可入口及至多一个活动购买任务；旧会话以确定性映射保留，不合并改写历史。没有跨设备或清 cookie 后恢复承诺。
- 持久记录任务、独立运行、输入、入场版本、状态、可靠结果/消息及回执。运行状态区分进行中、等待澄清、等待确认、自然完成、保护终止、已停止和失败；任务完成/放弃单独记录，不能由运行终态推断。
- 新消息先经可信请求登记与相关性处理：事实问答不改购物任务；进度读取不打断；条件修订立即记录并确认回应。可继续有用的在途只读调用，但提交/交付最终方案必须验证新条件。原 run 不得把当前版本偷换成入场授权版本；需要重算时形成受新版本约束的后续处理。
- 停止处理与放弃任务为不同命令。停止确认和业务提交在权威短事务中按顺序决胜：停止先成功则后续提交被 fence 拦截；提交先成功则返回实际回执，不能自动反向删除。放弃/换任务使旧执行失效，但保留购物车事实。
- SSE 连接只是传输，断开不等于停止。已启动运行可在既定预算内继续并落库；重新连接按运行/消息序号恢复结果。进程故障后先恢复已提交回执；不能盲目重跑不确定写操作，不承诺任意机器故障都继续模型执行。

### 3. 有界真实 runtime 与交互事件

- Pi 必须实际读取工具结果后决定下一步。只读工具覆盖当前目标所需检索、供给、比较、当前任务/车及授权可见背景；只准备提案，不能直接加购、结算或创建售后申请。候选引用、金额、库存及业务 ID 均由服务验证。
- 每次运行最多 **5 轮工具循环**：一轮为模型决定→执行一批工具→读取结果；批内多工具不按多轮计数。15 秒从宿主接受并登记该运行开始计入启动/模型/工具探索；任一上限先到即关闭新工具闸门并请求取消在途探索。无需用满预算；澄清、确认等待与可靠完成可更早结束。
- 达限时不启动额外无预算总结模型调用。优先使用已验证事实形成确定性的有限收口：已得到什么、还缺什么、此次已停止探索及是否继续由用户决定。尚未拿到可靠事实就明确说明；有已提交回执须如实报告。合作取消不能保证 provider 立即退出，迟到输出不得产生新副作用或改写终态。
- 15 秒不是任意复杂任务完整成功或最终 LLM 文本必达的保证。分别记录探索截止、收口可见时间、在途取消时间；收口走不依赖新 LLM 的有界路径。保护终止不是任务成功，也不自动创建下一运行。
- 用户事件仅含实际业务动作与安全事实：工具时一行灰字，新动作滚动替换；准备回答显示三点，再流式输出，支持多条自然短消息与适度 emoji。没有“1–3 条”硬上限。不得展示内部推理、原始私密工具参数或尚未提交的成功。
- 依赖固定可核验版本和 lockfile；Pi 公开 API/provider 兼容性以已核查研究为起点，实施时做真实集成验证，不能以自己编写的循环或脚本模型代替 SDK。LangGraph 同理须实际编译/执行持久图；checkpoint 恢复不是业务授权。

### 4. V1/V2 采购、比较与确认

- 完整保留单菜/直接商品准备、pantry 默认不选、改选修订、任务预算与排除、供给预览/部分采购、明确确认、检索证据及页面/品类上下文。
- 完整保留 V2 单菜人数与余量、多菜分组/兼容食材合并再取整、行级已购记录、规格供给适配、可乐示范的品类筛选比较。金额采用既有分金额，数量由确定性需求/包装服务计算；规格选择不能在后续改人数时丢失。
- 比较只使用真实候选属性，缺失信息标未知；查询失败不能说成无货。替代不得静默放宽预算/排除或自动选定新目标。接受具体报价可更新预算，但不是确认加购。核对车中实际数量避免重复采购，不能把任何购物车自动解释成新菜谱。
- 按钮与明确聊天加购共用一个确认契约：绑定 owner、活动 task、唯一已展示 proposal/plan revision、SKU/数量、金额/供给及 idempotency key。自然语言只负责识别明确指令，宿主解析唯一当前对象并验证；“好的／可以”、选定候选、旧消息或模型声称同意都不构成泛化写授权。
- 影响提案的条件、商品、数量、预算或供给变化使旧确认失效；重新展示并确认。确认事务重验归属、版本、资格/库存、预算和已购 ledger，业务副作用与回执原子写入。相同 key 同正文重放原回执，异正文冲突。货架直接加减与逐行显式加购保留自身明确用户动作，不被强迫绕经模型。

### 5. 四类记忆、Dream 与历史复购

- SQL ShoppingMemory 继续为 user/feedback/project/reference 唯一记忆权威；保留显式/自动来源、有效期、显式优先和当前条件优先。聊天 CRUD 可查询全部有效记录；用于模型召回沿用最多 5 条/2,000 字符。没有独立记忆管理设置页。
- 可可与墨墨共享可信用户身份，只按业务需要召回相关背景；订单、供给和业务授权不能由记忆替代。reference 保留可追溯来源，不凭自由文本构造订单或授权。禁止跨用户访问，也不默认全记忆对两角色开放。
- 已提交合格轮次回复后持久安排自动提取，主回复不等待；独立模型配置不静默回退主模型。保留 30 天自动记忆有效期、至少 10 条有效自动记忆且距成功 Dream 至少 24 小时的整理门槛；不变内容不无限续期。
- 后台记录待处理/运行/完成/失败及来源唯一性，支持本机重启恢复、过期租约、每用户单有效 Dream；提交前重验 source/revision，显式更正/删除优先，迟到结果不得复活删除内容。助手建议、单次预算/人数不自动升为永久偏好。此后台只整理记忆，不启动购物监测。
- 当前新任务可提醒相关、仍未解决且近期未问过的历史清单一次；先核对购物车，忽略或拒绝后停止，不自动恢复任务/授权。用户选定历史方案后生成本次新任务/清单和来源引用，应用当前条件、需求/包装与供给；旧金额、库存、已购 ledger 和确认不得继承。

### 6. 模拟订单与 Mercury 状态契约

- 独立模拟结算读当前 owner 购物车并展示版本化摘要；确认后一个事务创建订单、不可变商品/价格/数量/规则来源快照、结算回执并移除本次结算项。并发新增不得被清空；重放不再下单，变化要求刷新摘要。旧浏览器 LocalOrder 不自动升级成可信订单。
- 订单与售后共有单一权威，墨墨选单控件绑定真实 owner-scoped order ID；无订单就返回空，不回退 demo owner。固定订单状态、可退属性和签收时间来自业务服务或隔离 fixture，普通用户不能设状态来获得资格。
- LangGraph 明确阶段为查询/补信息→资格→提案→等待确认→重验并幂等提交→回执；不符合资格解释原因，信息不足先问。持久 case/checkpoint 绑定 owner 和订单引用，thread ID 不是访问凭据。恢复 interrupt 可重跑节点，故不可在等待节点前偷偷写申请。
- 初次退款/退货意图只生成提案。提案含订单/商品、范围/数量、预计金额、原因、适用规则与事实版本；确认绑定不可变提案版本。换对象、变数量/原因、资格变化或过期须重新生成并确认。过期策略由有效业务契约实现并展示，不继承旧草案未确认的“15 分钟”产品承诺。
- 暂沿用有效 Mercury 资格与金额政策：整单未发货仅退款、已签收且可退的单明细整行退货、原 7 日期限与现有申请状态；不新增部分件数/多行批量或参考项目金额阈值。对 cancelled 等实现可能放行的缺陷须按既有有效政策核查修复，不把代码漏洞当新增资格；时间迁移须明确 UTC/旧时区，不擅自解释未知旧时间。
- 确定性提交在同一事务验证 owner、case/proposal 版本、人工 hold、资格与确认，claim operation，写申请及 receipt。现服务内部独立 commit 须调整为可组合事务。业务已提交但 checkpoint/模型失败，恢复先读 receipt，不重复申请；pending/requested 不说成退款到账、审批完成或真实履约。
- 主参考为 WangWeiqiang-UCAS/E-commerce-Smart-Agent 的电商阶段与 NanGePlus/LangGraphChatBot 的多轮客服/持久化/RAG 设计。两者仓库级许可证未核实，仅参考架构和独立适配，不复制代码或假定兼容。其他项目为辅助对照，不重新开放主参考选型。

### 7. 精简异步人工工单

- 用户明确要求人工、政策无法确定、业务服务持续失败时创建持久工单；同一未解决事项去重，关联 owner/case/order、必要问题摘要与对话历史。信息不足先澄清，明确不符合资格解释，不承诺人工例外批准。
- 小型人工后台提供受保护的查看、回复、补充追问、解决/关闭；用户端可看进度和回复，不做实时接管。采用必要的可信 operator 身份/权限，不能向普通用户开放员工接口，也不借此建设完整员工账户/排班平台。
- 工单人工负责期间，case 的责任状态与 generation fence 阻止 Agent 独立提交同事项业务写；只暂停图不够，在途写必须在事务中重查。此前已提交结果照实显示。人工回复不是用户授权，不直接退款，也不能绕过原资格。
- 关闭/解决保留完整记录；后续需要 Agent 处理写动作时，重新核对当前责任、资格和具体提案/确认，不自动恢复旧批准。后台只覆盖最小生命周期，不做 SLA、运营分析或人员排班。

### 8. 数据与迁移随切片交付

- 每个使用新状态的纵切片包含最小隔离 seed、schema/迁移（需要时）、API/UI 与行为验证；没有需求就不添通用平台。fixture 至少覆盖两 owner、菜/商品/包装/缺货、订单状态和固定时钟，绝不从活动库补 fixture。
- 增量迁移验证空库、合成旧库、重复执行和事实保全；回退保留订单/申请/回执，不重新开放旧无确认写入口，必要时只读/hold。旧 Mercury 演示数据仅在明确 owner mapping 与时间语义后离线迁移，无映射保留隔离，不能归给首个用户。
- 两 runtime 首切片各自使用最小 fixture 与已有服务接缝，带入真正阻塞其演示的最小修复；不把全部人数/多菜/采购恢复并入前置。缺失 fixture、ContextPlan、比较/记忆接口等债务在实际受影响切片修复，不能用删除断言、skip 或历史通过掩盖。

## Testing Decisions

### 已确认的两级接缝

1. **主接缝：现有公开 HTTP/SSE＋刷新/重启后的业务可见结果，页面作独立端到端验证。** 从用户请求检验任务、候选、方案、购物车、订单、case、工单、消息和回执；不依赖内部图节点数或方法调用次数。
2. **唯一补充的事务服务接缝：Python 业务操作提交接口及其 unit-of-work。** 精确覆盖三类写边界：确认加购（沿用 ConfirmationService/CartService 的事务组合）；模拟结算（订单＋本次车扣减＋receipt）；售后提交（资格重验＋申请＋receipt）。只在该边界注入提交前失败、提交后响应/checkpoint 丢失和并发 fence，再用公共读取验证结果。不是给每个内部 helper 各建测试抽象，也不以 checkpoint 作为账本。

以上测试接缝已于 14:09 UTC 经用户针对性确认，不再为同一测试边界重复请求批准。Pi/IPC 与模型 provider 的传输契约测试、真实 LangGraph 恢复验证是 runtime 集成证据，不另造业务权威。

### 测试原则、先例与必要覆盖

- 复用现有确认/并发/修订、单菜人数、多菜需求、供给、比较、显式/自动记忆及 Mercury service 测试族；它们提供行为断言先例，历史通过不是当前证据。
- 使用实际 Pi SDK 与实际 LangGraph 执行受控测试，允许在模型边界注入确定性 fixture；另行真实 provider 采样证明自主决定与工具兼容。手写替身循环不能证明采用 runtime，脚本模型不能证明真实模型效果。
- 每个 runtime 首票包含请求→runtime→真实领域服务/隔离数据→用户可见结果；分别证明只读查询与多轮/恢复，而不是只安装依赖。后续每个切片完整跨过 schema/服务/API/UI/验证。
- 必测两 owner 隔离、伪造对象/候选/授权、同 key 重放与异正文冲突、条件修订的旧版本失效、停止前后提交竞争、关页继续/重连持久结果、5 轮与 15 秒边界及早停/等待。达限后不再发工具、不用新模型收口、不自动续跑。
- 必测自然语言明确加购与含糊 ACK 的区分、方案变更重确认、人数/多菜/供给/比较原业务、购物车重复防护、记忆删除不复活、Dream 故障恢复、复购重查/重确认。
- 必测结算原子性、订单快照/隔离、资格/金额/期限、首次售后意图不写、确认重放、提交后 checkpoint 失败、人工工单触发与进度、人工归属和在途 Agent 写竞争、关闭后不复用旧授权。
- 迁移需验证重建/重复升级/保存旧事实/安全回退；测试入口和 import/startup 不能触碰原活动库。每个新增 V2 场景两次独立自动行为验证，保留真实命令、退出码和输入版本。
