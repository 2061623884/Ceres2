# Ceres2：真实 Kev 基线与导购质量改进规格

规格与测试接缝：2026-10-09用户已确认；10票任务图同轮确认，见[任务图](ceres2-kev-quality-followup-tickets.md)。正式任务状态由[04总TASK](../../tasks/ceres2-local-followup-04-real-evaluation-feedback.md)及各票维护。进入implement-spec不代表技术或本人验收通过。

## Problem Statement

用户需要一个能正确理解购买需求、找到在售商品、适时澄清并形成可确认采购清单的导购，也需要可复现的测试、真实评测和反馈闭环来判断优化是否有效。

上一轮真实100次机器判分为66通过、30失败、4未知，但Ceres2没有配置真实Kev地址，角色入口全部走了缺配路径。Kev还参与政策预取，因此旧结果不能直接用于判断真实Kev效果，也不能在补齐环境后把分数变化全部归为商品修复收益。公开样本暴露了在库商品被答成无匹配、缺少澄清、未生成购买方案和购物/政策混合请求处理不足；当前证据尚不能把这些现象统一归因于检索算法。

真实GraphRAG独立构建与查询已有证据，正式100次却没有图调用。当前图工具用于显式菜谱关系探索，普通菜谱事实有现成路径，因此零调用本身不证明接入失败；独立查询约18秒，也不满足Guide当前15秒总运行时限。多消息数量、一次模拟订单旅程或合成Dream通过，同样不能代替自然度、完整页面、售后及记忆生命周期验收。

## Solution

先连接用户在amax GPU1部署的既有Kev，验证实际Ceres2角色路由和政策预取，建立补齐环境后的新基线。基于这条基线的公开失败，整理8–12条代表样本及标注草稿，由用户确认期望和判定，再做有证据的最小修复及同条件回归。

在真实Pi中对明确需要菜谱关系探索的任务做图/无图对照，只有质量与15秒时延均达标才让图能力进入核心导购；否则保留独立显式图查询，核心继续使用已有菜谱事实与混合检索。最后以固定候选完成实际界面、消息自然度、当前LangGraph售后和Memory/Dream验收，并交付版本、失败、未测项和可追溯对照报告。

## User Stories

1. 作为导购用户，我希望具体已下单订单问题被建议交给墨墨，以便进入正确的售后流程。
2. 作为导购用户，我希望一般门店政策、商品选购和普通聊天留在可可，以免无必要地切换角色。
3. 作为导购用户，我希望切换建议由我接受或拒绝，以便保持对当前对话的控制。
4. 作为导购用户，我希望接受切换后原始需求完整交给下一位助手，以免重新描述或丢失条件。
5. 作为导购用户，我希望拒绝切换、刷新或重复提交不会重复判断或产生业务操作，以便安全地继续对话。
6. 作为产品经理，我希望服务缺配、超时、协议错误和分类错误分别记录，以免错误评价Kev能力。
7. 作为产品经理，我希望补齐Kev后重新建立基线，以便将环境影响与产品优化分开比较。
8. 作为购买用户，我希望明确品牌和规格的在售商品被找到，以免收到错误的无匹配结论。
9. 作为购买用户，我希望人数、件数、预算和排除条件被正确保留，以便得到符合需求的采购安排。
10. 作为购买用户，我希望已选定商品和明确数量能形成可检查的采购清单，以便决定是否加购。
11. 作为购买用户，我希望购买对象或规格存在实际歧义时收到必要澄清，以免助手猜测。
12. 作为购买用户，我希望缺货、超预算和合法报价等待得到如实说明，以便作出下一步选择。
13. 作为购买用户，我希望商品需求与一般政策问题在同一请求中都被处理，以免其中一部分被覆盖。
14. 作为购买用户，我希望采购清单在我明确确认前不进入购物车，以便保持业务授权边界。
15. 作为菜谱用户，我希望多个菜谱之间的关系问题得到有依据的答案，以便发现合适的做菜方向。
16. 作为菜谱用户，我希望普通已知菜谱查询保持及时，以免无必要图查询拖慢购买流程。
17. 作为产品经理，我希望看到真实Pi的图调用、结果和时延，以便判断图检索是否有实际收益。
18. 作为产品经理，我希望图收益来自同条件任务对照，以免把组件成功或工具可调用误当成业务改善。
19. 作为产品经理，我希望公开失败样本带当前事实、期望和标注草稿，以便亲自确认错误分类。
20. 作为产品经理，我希望人工标签保留实际确认人和时间，以免把Agent审阅记成人工验收。
21. 作为产品经理，我希望至少一组失败完成采集、人工标注、修复、回归和新旧对比，以便证明反馈闭环成立。
22. 作为产品经理，我希望独立验收样本不进入调参数据，以便保留明确的评测边界。
23. 作为聊天用户，我希望复杂任务按需要发送有价值的过程消息，以便知道进展而不被重复套话打扰。
24. 作为聊天用户，我希望简单问题也能直接回答，以免消息数量被机械增加。
25. 作为页面用户，我希望商品详情、数量选择、采购确认与模拟订单操作连贯可用，以便完成演示闭环。
26. 作为售后用户，我希望针对正确订单形成售后提案，并在我确认后提交，以免处理错误对象或未经授权提交。
27. 作为售后用户，我希望重复确认、停止和恢复不会产生重复申请或迟到发布，以便可靠地处理事务。
28. 作为长期用户，我希望记忆能保存、读取、更正和删除，以便偏好服务于当前需求且受我控制。
29. 作为长期用户，我希望后台提取与Dream不阻塞主回复，也不恢复已删除内容，以便记忆生命周期可靠。
30. 作为验收者，我希望看见实际通过、失败、未知和未执行项及对应版本，以便判断这一轮完成了什么。

## Implementation Decisions

- 保留同一集成工作树和分支；已发布版本是前次基线来源。此次不合并、不推送、不部署、不修改原工程或用户既有Kev服务。
- Kev是用户在GPU1部署的真实服务；仅通过既有HTTP协议连接。角色判断与政策预取分别留证，继续使用当前模型标签及3秒调用上限。
- 角色切换只是建议。用户确认前不改变角色、不执行订单/售后写入；原文、身份、选中对象、请求重放和拒绝行为遵守当前公共合同。
- 隔离评测服务只读使用获准的主模型与Memory配置，使用独立新业务库和checkpoint，保持生产MemoryWorker开启；不迁入原会话、购物车、订单或索引。
- 新环境基线保持现有40公开/20独立验收输入和评分规则：20公开核心各3次，其余40各1次，共100次；先20次pilot，服务与采集无系统性阻断后同版续跑。
- 旧缺配批次保留原始66/30/4。新环境基线与后续产品候选分别冻结代码、实际源码、模型、Prompt、语料、索引、执行器和评分器版本。
- 公开商品问题按当前供给事实、候选召回、业务过滤、Pi工具决策、方案校验和发布逐层定位。先取得必要证据再决定改动层，不预先重写检索或后端。
- 购买方案、合法等待和澄清是不同业务结果。明确对象与数量允许形成清单；歧义需有效澄清；接受报价不等于确认加购。
- 用户确认8–12条公开样本的人工标签。Agent只准备草稿和分类建议；未确认的标签保持待审，不记成人工通过。
- 至少一组已标注公开失败纳入回归，经最小修复、同条件采样和版本对比形成完整反馈链；私有验收题面不向实施者开放。
- GraphRAG继续以显式关系需求为入口。对照通过真实Pi运行，工具可用性是消融时唯一预声明变量；不提前给产品增加无调用方开关。
- 15秒/最多5轮及模型额度保持当前合同。Guide运行耗时与从角色入口开始的页面总耗时分别记录，独立图查询的180秒预算不能替代核心时限。
- 图进入核心须证明任务质量收益与时延均达标；未达标时保留独立能力，不承诺本轮强制进入核心链路。
- 售后验收使用当前Python LangGraph能力；Python继续作为业务事实和写入权威。价格、库存、订单、支付、退款与配送仍为模拟。
- 维持现有业务接口、授权和事务合同；不预先新增业务表、兼容层、重试或宽泛抽象。执行、评分及产品修改指定唯一维护者，避免共享入口并发修改。

## Testing Decisions

- **主要业务接缝：**用户可见的公共HTTP/API/SSE；通过实际角色路由、商品结果、采购清单、澄清、确认回执和持久化后可再读取的业务结果验证行为。
- **评测接缝：**已有采集、评分、标注、失败归档和版本比较CLI；验证输入/来源绑定、完整分母和未知证据处理，不以评分器自身实现推导期望值。
- **体验接缝：**当前构建版实际浏览器。接口和受控DOM通过不代替用户页面操作或本人自然度接受。用户已明确确认上述三类接缝。
- 优先复用现有导航公开合同、采购确认/幂等、真实SSE、图运行、售后生命周期和记忆删除保护的测试方式。只针对当前失败增加有意义的公共行为测试，不测试私有实现形状或写重复实现的断言。
- 专职Tester独占测试、lint、typecheck、build、安装验证、服务启动和真实模型采样；实现者先准备RED，观察失败后最小实现，再请求GREEN与适用回归。
- Kev先测真实服务协议及有限中文正负例，再通过Ceres公共导航验证接受、拒绝、原文交接、同请求重放和政策预取。计数不能归因时记未知，不以相同响应冒充没有重复调用的证明。
- 真实采样固定计划，包含准备失败、执行器失败、模型失败、等待、保护终止和未执行；失败不重跑冲成绩。正确角色等待/澄清与任务成功分别判定。
- **本轮产品修复门槛：**修复前冻结公开问题清单，受影响场景各独立3次均满足业务条件；最终完整100候选与新环境基线检查新增退化、关键违规和15秒时限。剩余失败逐项保留，不要求或宣称100次全部业务通过。
- 图对照单列预声明关系任务、两臂相同重复次数、实际调用/成功/超时和最终答案质量；主模型输入输出与可观测usage按覆盖率报告，费用未知保持未知。
- 综合体验覆盖实际Guide多轮与消息、商品/数量/确认/模拟订单、正确目标订单售后与幂等、记忆CRUD/真实提取/Dream门槛与冷却/删除后不复活。合成Dream和自然会话触发证据分开。
- 在最终候选执行适用完整回归、Pi/前端类型与构建以及必要真实浏览器验证；Standards与Spec独立只读审查。历史通过、新技术验证、真实质量和用户本人接受分别记录。

## Out of Scope

- 真实商业交易、支付、配送或退款履约，扩展订单后端为完整生产系统。
- 重写Pi或LangGraph、恢复旧Mercury工程、整体迁入旧运行库或索引。
- 活动提醒、跨回合自主通知，或以固定拆气泡代替自然多消息。
- 自动训练、无人确认的人工标签、新建无实际调用方的运营后台。
- 为提高分数更换已批准主模型、放宽15秒/5轮、删掉失败或改写原批次。
- 强制GraphRAG进入核心购买链路，或以小规模demo对照宣称统计泛化。
- 合并、推送、部署或调整用户GPU1服务；新增范围另经明确讨论。
