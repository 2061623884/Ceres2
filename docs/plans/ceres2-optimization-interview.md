- **Q7–Q10 采纳推荐**：按问题数量形成模拟申请；可关联照片供人工查看；用明确的模拟状态推进串起同一新订单；采用本地中文 embedding。具体 embedding 模型由架构方案选择，不能称用户已指定某个模型型号。

## 设计树与第一轮记录

以下保留首轮问题与推荐的上下文，当前采纳结果以上方“已确认范围与最新覆盖”为准。

### Q1：订单增减的业务对象

区分购物车内商品数量变更、新建/取消模拟订单、以及直接编辑/删除已有订单。建议完成购物车增减、模拟结算形成持久订单、进入详情和符合状态规则的取消；历史订单保留实际记录。若需要演示数据管理，另明确其入口和权限。

后续决策：可修改状态、部分取消/售后关系、确认对象、页面入口及任务场景。

### Q2：本轮 RAG 的检索范围

区分政策、商品、菜谱和记忆。建议先覆盖共享政策与商品；政策条款和 SKU 分别检索，在各自候选内做混合召回和 RRF，商品最终价格/库存仍读取权威数据。是否纳入菜谱与记忆由用户决定。

后续决策：语料来源、中文稀疏检索、embedding、分块和版本、融合与可观察检索证据；用冻结查询集对照单路检索与融合结果。

### Q3：主动互动覆盖哪些时间与触发

区分同次回复的多条自然消息、没有新用户消息时的当前任务跟进、以及用户离开后的跨会话提醒。建议包括多条有内容的自然消息和页面内当前任务的有限事件跟进；离线提醒的渠道、条件与偏好另需明确。例子：先呈现商品，再主动补充一条有依据的比较，插话后撤销过时的后续消息。

后续决策：触发事件、时机、优先级、停止/抑制、连续追问、重连和重启恢复，以及“有帮助/有打扰”的评测标注。

### Q4：政策“补齐”的交付层次

区分可查询解释、确定性资格判定和业务动作执行。现有规则没有把“生鲜买多了”和“生鲜腐坏”分成两条资格路径；讨论稿提出的质量问题处理需要明确的业务规则扩展。建议八个政策域有可追溯的解释与边界，同时为批准的质量/履约问题补资格与可执行方案，其他结果明确不可办理或进入已有人工流程。具体金额、时限、证据与动作逐类定案，不能仅因补齐说明就认为新动作已实现。需明确配送问答是否进入本轮。

后续决策：品类例外、时限、数量金额、证据、食品安全升级、来源核验、条款与规则关联及发布版本。补齐文档不自动增加补送、真实退款或赔偿执行能力。

### Q5：本地与云端的交付责任

云端当前正在讨论评测集与量化指标。建议 dots 负责评测方法、用例与评分规则；本会话负责产品/架构讨论、实现和可采集的业务与检索证据。共享 case/trace 字段、用例版本和评分接口指定单一维护者，先对齐两侧基线。本轮 worktree 保持独立，不自动合并任何线路。

后续决策：评测集构成、标注责任、独立验收集管理、指标分母与门槛、失败回流准入、比较方案和验收负责者。

## 第二轮记录：具体业务行为

以下保留发出的第二轮问题与当时推荐。用户答复与明确覆盖见上方“第二轮回复与产品重点”；这里的原推荐不能覆盖最新主动定义。技术实现参数由本会话结合来源与验证结果提出，不把所有可逆的实现选择都交回用户。

### Q6：主动跟进是否由停顿触发

选项是仅由当前任务的新事实/完成事件触发，或也因用户停顿而主动催问。推荐前者：例如先给候选，商品比较完成后主动补一条有依据的差异；无新信息时保持安静。用户输入、修改条件或停止后，抑制与旧条件相关的后续消息。既有 5 轮/30 秒探索保护继续生效；达到保护边界不自动新开一轮。

同次多消息仍可用于完成的阶段说明和有用建议；阶段消息、工具进度、最终结果分别观察，进度不能代替任务完成。已显示历史消息是否标记过时与停止迟到续发在实现设计中分别处理。

### Q7：质量/履约问题是否支持按问题数量申请

例子：同一订单买三盒商品，其中一盒损坏。选项是按问题的一盒形成申请，或沿用整行三盒处理。推荐按问题数量形成模拟申请；结合订单商品、已申请数量及已批准规则计算具体提案，展示对象/数量/金额，经明确确认提交。提交仍表示申请已提交，不自动表示质量已认定、已审批或资金到账。食品安全/伤害/赔偿诉求走已有人工事项流程。

此决策会增加现有只支持整单退款/整行退货之外的明确业务能力；不会把 `reason` 自由文本直接当成已核实的品质事实。具体规则尚未定案时不推导自动资格。

### Q8：照片证据是否进入本期

选项是本期支持上传并关联照片，或仅收集文字描述和订单/商品/数量。推荐支持关联照片，保留用于申请/人工处理；本期的模型不自动认定图片真伪或商品质量。是否某一问题必须附照片，在对应规则中另行明确，不能一概要求所有诉求上传。

### Q9：新订单是否支持完整模拟状态推进

当前结算形成 `submitted` 订单，没有普通用户的发货/签收写入口。若只预置 `delivered` 场景，无法证明同一新订单从选购到质量售后的链路。推荐在本期加入明确标识的演示状态推进：新建→模拟配送→模拟签收；未发货状态可确认取消，已配送/签收的问题走对应售后提案。保留原始订单快照及状态变化记录，取消和退款申请分别反馈。

### Q10：真实 embedding 的资源方式

选项是本地中文 embedding 模型或独立 embedding API。推荐先采用固定版本的本地中文模型，避免新增每次查询的外部 embedding API 依赖；具体模型、依赖安装和实际运行效果由专职 Tester 验证。现有文本对话模型配置不代表已提供 embedding 能力，不使用伪向量作为真实 dense 检索证据。

### Hermes 引用复核与 Ceres 接缝

2026-10-07 再次读取用户指定的[Hooks 文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks)和[API 源文档](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/api-server.md)：官方确有 `on_interim_message`，未结束的处理中公开助手文本可作为 `message.interim`，最终答案独立返回，私有 reasoning 不进入该事件。本文只借鉴机制，保持 Pi 与 Python 权威，不替换为 Hermes runtime。

当前 Pi `worker.ts` 已订阅 SDK 事件，但抑制 `message_update` 文本，只输出生命周期事件和最后的 JSON；Python `publish_result` 在整个处理完成后才将最终文本切为 `answer.delta`。因此，仅把最终文本切成多气泡不能满足“处理过程中发言”。需要真实中途消息从 Pi 经 Python 验证与持久化后，通过现有 SSE 进入前端；工具进度、过程发言、最终结果分别处理。当前普通聊天的 `validate_general_text` 和商家事实由宿主渲染的约束必须显式适配，不能通过新增原始文本输出绕开。

## 新提议：菜谱/商品关系检索（尚未采纳）

用户同意前述优化方向后，补充知识图谱 RAG 的想法，明确“只是提议不是要求”，希望独立评估菜谱检索增益。政策继续使用混合检索；不能把本提议记为替换商品检索、安装图数据库或实施完整 GraphRAG 的授权。

当前事实：`data/fixtures/recipes.json` 只有番茄炒蛋、蛋炒饭两道菜，记录基准人数、必需食材及用量、基础调料；`DishService` 已将食材关联到 SKU 并计算人数/包装需求，`PurchaseService` 与 `supply_service` 已处理多菜合并、已购数量及同食材规格替换。这证明现有实现有结构化关系和算术，不等于新增关系检索已经验证。

候选方案是保留政策/商品 hybrid RAG，在菜谱侧评估有来源的关系查询：菜谱→需要的食材→能够满足该需求的 SKU。商品品类是筛选维度，不能通过品类把不等价食材混成可替代品；SKU 的食材关联也不代表配料、过敏或营养事实。

需要分别讨论的收益：模糊描述找菜依赖语义召回和菜谱属性；从已有食材反查菜、展示缺项适合结构化关系查询；人数/顿数/整包数量仍由确定性业务计算；语义食材替换依赖用途、数量换算和经过核查的关系来源，不能因为图中可达就默认可替代。

当前建议先设计小型对照验证，以当前查询为基线，用同一份已核查的菜谱/食材/SKU 数据验证关系查询能增加哪些可观察能力，并记录数据补充本身的收益。未证明需要前不新增独立图数据库、社区摘要或自动实体抽取流程。是否将该验证纳入本阶段，留待用户选择；已经确认的多消息和政策检索主线继续保留。

已完成的[当前关系审计](../../work/ceres2-optimization/research/recipe-relations-audit.md)记录了实际覆盖、代码调用路径和来源限制；[方案与官方资料复核](../../work/ceres2-optimization/research/graph-retrieval-options.md)比较关系查询、图存储和 Microsoft GraphRAG；[最新完整流程规格](ceres2-optimization-spec.md#完整-rag--graphrag-的小型数据切片)给出输入和应观察结果。待决定的前沿是本期纳入这个小型关系验证，还是仅保留研究而按原主线交付；不重新询问政策混合检索、同次多消息或 UI 风格。
